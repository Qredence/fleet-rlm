# Fleet-RLM migration to Daytona v2.1 and Neon Object Storage

## Target behavior

Run chat and evaluation workloads on Daytona v2.1 Linux microVMs. Keep Postgres as the source of session, run, memory, and file metadata. Store uploaded inputs and successfully published artifacts in private Neon Object Storage on the same branch. Each chat turn hydrates its file manifest into local `/workspace` before execution and publishes completed artifacts before it finishes. A replacement VM can recover those files. Scratch files and unpublished checkouts are tied to the VM's lifetime.

Use one streamed Python worker per DSPy RLM invocation. Parent and child RLMs share the session VM and filesystem while keeping separate Python namespaces. A single invocation keeps its namespace across cells. An ordinary next turn starts with fresh Python globals and can read persisted Fleet history and files. Preserve the existing AI SDK v1 chat stream, run tree, tool budgets, skill routing, and memory approval flow. [DSPy RLM](https://dspy.ai/current/api/modules/RLM/) · [Fleet run orchestration](../backend/src/fleet_rlm/agent.py)

Use the live Neon `uploads` round-trip as evidence for direct S3 access. Run migration acceptance on disposable Neon branches, a dedicated private staging bucket, test-labeled Daytona resources, and separate MLflow experiments. Use synthetic fixtures for the sandbox, Volume, and DSPy checks below.

## 1. Live Daytona sandbox verification

1. Confirm the v2 API key's project, region, and compute tier. Unset `DAYTONA_API_URL` and `DAYTONA_V2_API_URL`. Identify the staging Neon branch and its S3 endpoint before issuing writes. Use separate secrets for each environment. Keep all DB, S3, model, and Daytona credentials on the host during application runs.
2. Build a versioned v2 image from a staged context containing the sandbox Dockerfile and bundled Skills. Inspect the context archive before upload. The current backend directory contains an environment file and has no tracked Docker ignore rules. Wait for the registered image to be ready in the target region. Run Python 3.13, import DSPy 3.5.0 and the chart and workbook libraries, and check access to `/opt/skills` and write access to `/workspace`. Record the image ID, region, architecture, and Git SHA. [Daytona image builds](https://www.daytona.com/docs/images) · [Fleet Dockerfile](../backend/snapshot/Dockerfile)
3. Create an on-demand ephemeral Linux VM with default-deny outbound traffic and finite create, idle, and lifetime deadlines. Check the returned state, wait within a 120-second startup budget, and exercise argv execution plus atomic file upload, download, and rename on local disk. Test a denied egress request and a request to the explicitly allowlisted fixture host. The application must also work with sandbox egress closed when the task needs only staged files and host-side DSPy tools.
4. Start a tagged Python worker with open stdin. Stream its response, deliberately interrupt the logs connection, and resume at the last processed cursor. Check that each control event and host call is handled once. Cancel a test worker with a sleeping descendant and verify containment removes both while a separately tagged sibling still responds. Run with one short idle timeout and one short wall-clock timeout in separate VMs. Observe provider deletion, then verify explicit deletion and cleanup on a failed or cancelled create. Record allocation IDs, state changes, cursor evidence, and process cleanup before removing the test resources. [Daytona 2.1.0 process API](https://pypi.org/project/daytona/2.1.0/) · [Linux sandbox timeouts](https://www.daytona.com/docs/linux-sandboxes#timeouts)

## 2. Live Daytona Volume and Neon verification

Run this provider experiment before enabling any mount in Fleet. Use a disposable Neon branch and test bucket. Create two Daytona **external bucket Volume resources** with disjoint prefixes for input and output. A Volume ID can appear once per sandbox. Use the Neon branch's S3 endpoint, signing region, path-style addressing, and project secret references. Attach the input Volume read-only and the output Volume read-write in the selected region. Keep ordinary scratch on local disk. [Daytona external bucket Volumes](https://www.daytona.com/docs/volumes#external-bucket-volumes) · [Neon S3 compatibility](https://neon.com/docs/storage/s3-compatibility)

| Live check | Required observation |
| --- | --- |
| Empty and populated prefixes | Record whether an empty prefix can mount. Upload seeded CSV and XLSX inputs from the host with the candidate Python S3 client. In a VM, confirm the expected SHA-256 hashes and workbook contents. A write through the input mount must fail. |
| Output behavior | Write and close new CSV, PNG, and XLSX objects sequentially. Read them from the host, verify hashes, and record visibility latency. Separately try temporary-file rename, in-place edit, and overwriting an existing output. Record supported and rejected operations individually. |
| Volume durability and isolation | Delete the VM, confirm the bytes remain readable through S3, and attach the same prefixes to a second VM. Present another session's mount view and confirm it cannot read the first session's sentinel. Record both VM IDs, Volume IDs, and hashes. |
| Branch consistency | Fork a disposable Neon branch after inserting a file record and uploading its object. Check the child sees both. Change the object and record on the child and compare hashes on the child and parent. Confirm the parent still has the original file. |

The serving migration uses local disk hydration and publish backed by host-side S3. Bucket mounts can be qualified for read-only datasets or sequential exports independently. Daytona documents that bucket mounts lack rename, symlinks, and in-place writes. A successful sequential write leaves those limits in place. A mount failure is a reported compatibility result. Direct host S3 access, VM replacement recovery, and durable publication remain release gates. [Bucket filesystem behavior](https://www.daytona.com/docs/volumes#bucket-volume-data) · [Neon Object Storage branching](https://neon.com/docs/storage/overview)

## 3. Implement the streamed DSPy interpreter and run the canary

Keep Daytona operations in `interpreter.py`. Use `daytona[v0-sdk,otel]` locked to 2.1.0 for the canary, with v0 for the comparison arm and v2 for the candidate worker and the optimizer's volume-free interpreter. The serving cutover uses `daytona[otel]` at the same version. Keep the interpreter factory at the existing DSPy invocation boundary and reuse Fleet's `execute`, `shutdown`, `FinalOutput`, tool observer, and execution observer contracts. [Current interpreter](../backend/src/fleet_rlm/interpreter.py) · [Daytona SDK migration reference](https://github.com/daytona/clients/blob/main/upgrade/MIGRATION.md)

- Start one tagged guest worker per root or child RLM using `process.start(stdin="open")`. Its stdin reader routes execution requests to the Python loop and tool replies to the matching blocked call. Use the SDK's authenticated log stream for bounded stdout, stderr, tool requests, and completion frames. Validate frame size, cell and call IDs, and tool names against the invocation's declared tools.
- Reconnect the output stream with the last processed cursor and deduplicate calls. A lost stdin acknowledgement, evicted log history, invalid frame, or exhausted reconnect budget fails the cell and tears down the worker. Fence late replies and await worker and descendant cleanup before admitting another root if cancellation or transport failure makes reuse uncertain.
- Preserve the active-Python watchdog that pauses while a host tool is running. Keep a separate hard turn deadline and produce a recoverable DSPy execution error for a timed-out cell once cleanup is confirmed. Start a fresh worker for the next cell after a timeout. Preserve namespace state across an ordinary Python exception. An uncertain teardown aborts the turn and invalidates its VM binding.
- Keep MLflow DSPy autologging and the existing `daytona.python.execute` spans. Add the stable Fleet root, run, and parent IDs where needed to correlate children reliably. Correlate SDK OpenTelemetry request spans when enabled, and test that enabling transport tracing introduces no credentials or presigned URLs into evidence. [MLflow DSPy tracing](https://mlflow.org/docs/3.18.0/genai/tracing/integrations/listing/dspy/)

Run the optimizer integration on on-demand capacity first. Then run a bounded Spot canary on its own isolated eval branch, with a synthetic dataset and a private output directory. Use the current `--target rlm --program rlm --auto light --num-threads 1` CLI shape with the explicit `--database-url` and `--dataset`. Verify the requested tier, result or terminal provider state, and cleanup. Record an observed provider reclaim when available and exercise recovery with an injected VM loss. GEPA output is evaluation evidence and stays outside the serving release. [Optimizer CLI](../backend/src/fleet_rlm/optimize.py) · [Daytona Spot behavior](https://www.daytona.com/docs/preemption)

### Live DSPy trajectories

Use the real DSPy `dspy.RLM` and the real Daytona sandbox in both suites. Run the scripted-action suite first so timeout, recursion, disconnect, and transport faults occur at known points. Then run five paired repetitions of each real-model workflow on v0 and v2 with identical fixtures, prompts, model and decision-model IDs, temperatures, Skills, and RLM limits. Disable LM caching. The model may choose different valid cell code and phrasing, so check normalized results, tool and artifact evidence, and causal order. [Existing live CSV test](../backend/tests/test_phase2_engine.py#L1320) · [Fleet evaluation baseline](evaluation-baseline.md)

| Suite and fixture | Assertions |
| --- | --- |
| **Scripted · Cell loop and recovery** | A root sets a global in cell 1, reads it in cell 2, recovers from a regular Python exception, and terminates through typed `SUBMIT`. Allow one pure-Python cell to hit the short evaluation timeout. Confirm reset clears the global and leaves staged files intact. A host tool that takes longer than that cell budget must finish with the watchdog paused. |
| **Scripted · Recursive dispatch and limits** | Force root → child → grandchild plus a separate `llm_query_batched` call. Assert distinct workers, one session VM, configured depth and shared sub-LM limits, exact callback counts through a stream disconnect, and a controlled error at the attempted next depth. Verify the parent reads the child's result before its own `SUBMIT`. |
| **Scripted · Stop during a child call** | Stop or disconnect while a child and its tagged process are active. The root and still-running descendants reach a terminal cancelled state. There are no late replies or committed partial artifacts. A retry runs with fresh globals. Repeat with a dropped provider stream and an intentionally removed test VM to distinguish cancellation from transport failure. |
| **Real model · Two-turn CSV recovery** | Upload a CSV containing `2, 5, 11`. The root reads it, delegates a calculation to an actual RLM child, verifies the child's result, and submits `18` with a valid chart. Require at least two root cells and child Python execution. Delete the v2 VM between turns. Read the chart from the API before the second VM exists. The next real turn uses history and the rehydrated file, reports `18; fresh`, and proves the previous Python global is absent. For v0 parity, use its normal second-turn reattach path. |
| **Real model · Reconciliation tree** | Give the root two CSVs with totals 7 and 11 plus short documents with two known classification labels. Instruct it to delegate the two subtasks, have one child delegate a verification to a grandchild, and use a batched LM tool on the document labels. Omit expected totals and labels from the prompts. Assert total 18, correct labels, the child artifacts and their content, a depth-two workspace RLM span, and a separate query run. |

For every successful real-model turn, require a typed `SUBMIT` in the observed trajectory. Score an extract-at-iteration-limit response as a miss for these cases. Verify that the parent cell opens before its child call, the child runs its own Python cells and completes, and the parent uses the returned result to finish. Treat `llm_query` and `llm_query_batched` as query runs with their own status and model evidence. A sub-RLM requires its own `RLM.forward` and Python execution spans. [DSPy trajectory API](https://dspy.ai/current/api/modules/RLM/)

```text
Root RLM.forward
  Python cell 1 — read staged inputs and retain state
  Python cell 2 — call spawn_agent and await the result
    Child RLM.forward
      Python cell — execute the assigned check
        Grandchild RLM.forward (depth-two case)
          Python cell — verify and SUBMIT
      Python cell — inspect result and SUBMIT
  Python cell 3 — reconcile results, write artifact, and SUBMIT
Fleet verifies and publishes the artifact, then completes the turn
```

**Evidence per repetition.** Save case and attempt IDs, session/root/child IDs and depths, model and budget settings, image and sandbox IDs, synthetic fixtures and hashes, artifact hashes, and terminal statuses. Save the ordered DSPy action and output trajectory for direct RLM canaries and the matching SSE Python/subagent events for HTTP turns. Retrieve the MLflow trace by stable run tags and verify span ancestry by IDs, allowing intermediary spans. Record worker IDs, timing, model calls and tokens, storage bytes, and cleanup outcome. Keep full synthetic trace payloads in the private evaluation directory. Record retries as additional attempts and keep the original failures. [MLflow search and filtering](https://github.com/mlflow/mlflow/blob/v3.18.0/docs/docs/genai/tracing/search-traces.mdx)

## 4. Integrate durable storage and cut over session execution

1. Add `storage.py` as an independent module for the host's path-style SigV4 `boto3` client. Reuse the existing multipart size limits and file path validation. Upload bytes to a unique key under the session prefix, verify hash and size, then publish the Postgres file record. Store the object key privately in the metadata. The API continues to expose workspace paths, hashes, and sizes. Keep blocking S3 transfer work off the event loop and keep database transactions short.
2. Reserve the VM allocation name in Postgres before sending the Daytona create request. Retry with the same name and configuration after losing the response. Bind the returned ID to the active root with compare-and-swap. Mark a VM for retirement in the same transaction that finishes an unsafe turn. Start a fresh VM after Daytona confirms the previous one is gone. File operations can run on a cold Session without new compute.
3. Treat uploaded inputs and committed artifacts as the durable manifest. Before executing a root turn, reconcile its managed local directories against the committed manifest and verify staged bytes. Hydrated inputs are working copies. Save edits as artifacts for durable retention. Only serve scratch browsing from an already-running VM. Cold browsing, upload, download, and Skill install use the durable store and metadata. The worker runs without host storage credentials. Select and publish regular files beneath `/workspace/artifacts` after execution closes. Persist the file records and completed turn together after S3 writes succeed, then emit artifact availability and terminal success. Cancelled or failed turn outputs cannot be published by the next turn.
4. Register each S3 multipart upload ID before sending file bytes. Record superseded keys in the same transaction that publishes their replacements. Reclaim those objects after commit, and refresh the manifest for a reader whose selected key was reclaimed. Fence Session deletion while a root or live upload lease is active. Keep the pending Session visible for retry. Abort abandoned multipart uploads before deleting the Session’s objects so an expired writer cannot publish after cleanup.
5. Update environment examples, settings status, architectural contracts, and the existing evaluation runner. Set the v2 image, region, S3 configuration, network policy, and VM lifetime policy in deployment configuration. Default to 15 minutes idle and a maximum lifetime of eight hours. Use on-demand chat capacity and allow Spot for the isolated optimizer. Keep infrastructure status read-only in the Settings API. After the candidate passes, remove v0 runtime calls and the `v0-sdk` extra. [Neon object API behavior](https://neon.com/docs/storage/s3-compatibility) · [Current session and upload paths](../backend/src/fleet_rlm/api.py)

## 5. Cutover and release gates

- **Go/no-go.** Require all sandbox, host S3, scripted trajectory, and full-stack correctness checks to pass with no missing trace or surviving test worker. Require five successful candidate repetitions per real-model workflow with no paired regression. Use the 120-second startup bound and flag a warm execution median more than 25% slower than the fresh paired baseline for review before rollout. Report the Volume experiment and Spot capability alongside the required gates. A skipped required run leaves its gate pending.
- **Data rehearsal.** On a disposable Neon branch, apply Alembic with the direct connection and verify sample v0 binds and stale file metadata are cleared, old artifact controls are removed from saved run snapshots, and titles, textual history, run relationships, memories, and server-side Skills survive. Retire old Daytona workspace override keys and validate the new region in deployment configuration. Compare before and after counts and exercise the same-path upload case to catch stale links.
- **Live cutover.** Drain v0 writes and workers, save a Postgres restore point, apply the rehearsed migration, and deploy the verified v2 image and host configuration. Use a live smoke session to verify create, recursive execution, MLflow trace, artifact download, forced VM replacement, and clean delete before reopening traffic. Preserve the old Volume and deployment checkpoint during verification. Roll back by restoring the checkpoint before reopening if a gate fails. After live v2 writes, preserve the new Postgres and S3 state and fix forward.
- **After reopening.** Check provisioning and hydration errors, warm and cold latency, VM allocations and cleanup, file publication failures, and missing trace correlations. Retire v0 runtime credentials and resources once smoke and cleanup evidence are recorded. Keep the run IDs, trace IDs, and evidence location in the release record.

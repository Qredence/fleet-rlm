# P36 ownership and deletion contract

> **Historical record (P36, completed).** Rows name symbols deleted in P36; the
> document is retained as migration evidence, not as living architecture
> guidance. Current ownership rules live in `docs/reference/codebase-map.md`.

Status: **sealed gate artifact for P37-P40**.

P36 establishes the ownership and parity contract for the subtractive work that
follows P35-E. It does not delete implementation code. P37, P38, P39, and P40
must cite the inventory IDs below for every absorption, narrowing, or deletion.
The contract freezes ownership and observable behavior, never private Python
filenames, helper names, class layouts, or file counts.

## Gate and scope

P35-E was a hard prerequisite while the certification manifest machinery
existed. That same-SHA gate has since been retired together with the one-shot
P-certification receipts; archived manifests and live receipts remain ignored
local evidence under `.fleet-evidence/`, referenced by digest and path, not
copied into this document. Deletion-oriented changes now gate through the
standard release checks:

```bash
make check
make check-release
git diff --check
```

The inventory covers:

1. P37 Turn preparation, execution, local ownership, durable settlement, and
   cleanup;
2. P38 native DSPy execution, compatibility seams, repair behavior, and
   observability;
3. P39 recursive child acquisition, lease, late ownership, cleanup, and policy;
4. P40 explicit Session Workspace and Project hosts;
5. cross-cutting public behavior and certification gates.

## Decision vocabulary

| Decision | Meaning |
| --- | --- |
| `KEEP` | The named behavior or owner remains authoritative. A later change may move its implementation, but may not remove the obligation. |
| `ABSORB` | The current private boundary has no independent ownership in the target. Its behavior must be proven through the named owner before the boundary is removed or merged. |
| `DELETE AFTER PARITY` | The named compatibility or duplicate surface may be removed only after every listed deterministic predicate and required live predicate is green on one SHA. |
| `CONDITIONAL DELETE` | Deletion is permitted only after the explicit adoption or native-parity condition is recorded. Passing a unit test alone is insufficient when provider lifecycle or public evidence is involved. |
| `FORBID` | The surface must not be used or reintroduced. A zero-match or AST boundary check is part of the evidence. |

An **owner** is the authority for a behavior or resource, not necessarily the
module that currently contains it. A **parity predicate** compares public and
durable behavior, ownership, cleanup, and failure semantics. A filename is
evidence about the starting tree only; it is never itself a contract.

## Required deletion workflow

Before a P37-P40 change deletes or absorbs a row:

1. verify `E-BASE` against the current clean HEAD and `uv.lock` (an explicit SHA may only assert that same HEAD);
2. cite the inventory ID in the change description and tests;
3. run every deterministic entry named by the row;
4. run every required live entry serially, with confirmed provider absence and
   restored admission where applicable;
5. compare public Runtime Events, SSE, durable replay, Tool catalogs, and
   result shapes;
6. record failures as blocked deletion, not as evidence to reinterpret;
7. update the downstream feature's handoff with the inventory ID and receipt
   paths.

An implementation may consolidate several rows behind one owner, but it may
not use consolidation to erase a behavior obligation. A later P41 freeze may
remove private names that remain in this starting-tree inventory once the
owner and parity predicates are proven.

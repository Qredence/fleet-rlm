The module is organized around a clear separation of concerns:
- `turn_coordinator.py` is the public entry point (`TurnCoordinator.open`) that wires together the lifecycle, preparation, runner, projector, and cleanup supervisor. It owns delivery ordering and async orchestration (heartbeats, timeouts, cancellation shielding via `_shield_cleanup`).
- `turn_lifecycle.py` defines the `TurnLifecycle` protocol and `TurnLifecycleService`, which coordinates validation, artifact promotion, result snapshot writing, and atomic commit via an injected `_TurnStateStore`. It exposes typed start/finalize states (`BeginTurn`, `ExecuteTurn`, `ReplayTurn`, `CommittedTurnReceipt`, `FailedRunReceipt`).
- `turn_claim.py` holds the pure, side-effect-free claim transition policy (`decide_claim_transition`) shared by persistence adapters, with explicit `ClaimCommand` variants (`FailClaim`, `BeginSettlement`, `RevokeClaim`, `CompleteSettlement`, `HeartbeatClaim`).
- `turn_preparation.py` defines the `TurnPreparation` protocol and `DefaultTurnPreparer`, which builds an immutable `RLMExecutionContext` plus `PreparedTurn` before any streaming begins, managing staged attachments and capability cleanup.
- `deno_run_environment.py` and `capability_preparation.py` provide concrete `RunEnvironmentProvider` / `CapabilityPreparer` implementations for the Deno WASM path; they are swapped in at composition time.
- `committed_turn_events.py` projects durable `CommittedTurn` parts back into `RuntimeEvent`s for replay/live-suffix delivery.
- `turn_detail_policy.py` normalizes an `RLMOutcome` into the canonical `CommittedTurn` contract, enforcing tool call pairing and prediction presence.
- `session_context.py` builds a bounded `SessionContextManifest` of recent message previews passed to the interpreter.
- `run_authority.py` provides a per-run `RunAuthority` flag used to gate commits after claim loss.
- `turn_cleanup.py` runs detached cleanup tasks through a bounded `TurnCleanupSupervisor` so cleanup cannot leak or block callers.
Dependency direction: coordinator → lifecycle + preparation + runner + projector + cleanup; preparation depends on capability/session context; projection and detail policy depend only on event/committed-turn models.
